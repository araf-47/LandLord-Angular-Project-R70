UI/UX Design Plan v1 — full session summary (2026-08-29). Source doc: `moving-forward-plan/ui-ux_design_plan-v1.md`. Plan file used: `/home/araf/.claude/plans/shimmering-sprouting-stonebraker.md`.

Session ran in three passes, each verified with `ng build --configuration development` on both apps before moving on. Two commits: `f50b416` (first slice) and `2324e27` (rest of plan).

**Pass 1 — shared infra + proof-of-pattern slice.** Built `ToastService`/`<app-toast-host>` (signal-backed) and `ConfirmService`/`<app-confirm-dialog>` (promise-based, focus-trapped, Escape-to-cancel) independently in both apps' `shared/`, mounted once each in `app.html`. Added `--space-*` tokens and `.text-success`/`.text-danger`/`.mb-*`/`.gap-*` utilities to both `styles.css`. Wired the pattern into a representative slice to prove it end-to-end: LandLord's `ledger.component.ts` got real loading/error/ready states; `properties/unit-list` + `property-list` delete actions and BariVara's `owner/properties/unit-list` delete now use the confirm dialog instead of native `confirm()`; `tenant/payments/history` uses a toast instead of `alert()`; BariVara's `owner/listings/listing-list` delete — previously **unguarded, no confirmation at all**, a gap found during research — got the same dialog; BariVara's `listing-detail.book()` got a loading/disabled button state plus success/error toasts. `aria-expanded` added to all 5 hamburger menu-toggle buttons.

**Pass 2 — loading/error rollout.** The plan's headline finding was that only 1 of 56 LandLord components handled loading/error at all. Delegated to two parallel agents (one per app, following the exact pattern proven on `ledger.component.ts`) to roll `status`/`error` signals out to every remaining fetch-on-load component: 24 in LandLord, 10 in BariVara, 34 total. Handled naming collisions where a component already had its own `error`/`status` field (renamed to `loadError`/`pageStatus` etc. in those files). Message-thread components (Phase 12's polling screens) only wrap the *initial* fetch, not the 10-second poll loop. Form components used for both create and edit treat "nothing to fetch" (create mode) as immediately `ready`. Both apps re-verified clean.

**Pass 3 — everything else in the plan.** Asked you first whether to build dark mode or drop it (plan explicitly calls this a decision, not a default) — you said build it. Then:
- Killed all 79 remaining inline `style="..."` attributes (45 LandLord, 34 BariVara) via two more parallel agents, replaced with utility classes (`.mt-*`, `.max-w-*`, `.flex-between`, `.img-thumb`, `.topbar-plain`, `.sidebar-logout-btn`, a handful of narrow one-offs). Found and fixed a real bug along the way: `style="color:var(--color-danger, #c0392b)"` in 3 places referenced a token that was never defined anywhere in `styles.css` — it had always silently used the hardcoded fallback hex, never the actual design system. Now uses the real `--danger` token via `.text-danger`.
- Audited badge color contrast by hand (all pairs pass WCAG AA, 6.37:1–8.06:1, several pass AAA) — no changes needed, just verified.
- Added `:focus-visible` outline to `.btn`/`.module-tile`/`.listing-card`/links/buttons (previously only form inputs had a focus ring).
- Added a 1100px mid-breakpoint so `.module-grid`/`.listing-grid` collapse to 2 columns before the existing 860px mobile-drawer swap, instead of jumping straight from desktop to mobile.
- Built dark mode: `[data-theme="dark"]` token remap in both `styles.css` (same variable names, no component changes needed), a signal-backed `ThemeService` per app (localStorage-persisted), and a floating toggle button mounted in `app.html`. Badges deliberately keep their light chip backgrounds in both themes (small, self-contained, stay legible either way).
- Built `<app-stat-tile>` (LandLord `shared/`), replacing hand-rolled `<h2>` stat markup in `dashboard.component.ts` (5 tiles) and `ledger.component.ts` (3 tiles). Ledger table rows now get an income/expense left-border tint in addition to the badge, for faster scanning.
- Both `message-thread.component.ts` files (landlord + tenant) got a disabled "Sending…" button state and an error toast on send failure, without touching the existing 10-second poll loop.
- BariVara's 4 "No photo" placeholders (browse, homepage, favorites, listing-detail) replaced with a house-icon + "No photo yet" label on a brand-tint background, instead of a flat gray gradient. (Root cause — `VacancyAdSync` carries no photo field, so landlord-linked listings show this permanently — is a backend gap, noted but out of this pass's scope.)
- Added active-filter-chips to `browse.component.ts`: one clearable chip per set filter (search text, district, area, property type, source) plus "Clear all".
- Checked BariVara/LandLord dashboard visual parity — already true structurally (same token system, same `.module-grid`/`.module-tile` pattern), no code change needed.
